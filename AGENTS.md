# Agent notes for Composa

## What this is

Composa is a from-scratch implementation of the macOS image editor [Compositor](https://github.com/robbietilton/Compositor). The upstream app is Swift on AppKit, SwiftUI, CoreImage, Metal and Vision, none of which are portable, so nothing is shared at the source level: this repository reimplements the same feature set in C# on .NET 10, Avalonia 12 and SkiaSharp 3. It is developed on Linux and released for Linux and Windows; macOS is planned, so keep new code free of platform assumptions. CI runs the whole suite on Windows as well.

## Layout

- `src/Composa.Core`: everything that is not UI. Document model, compositor, selections, brush engine, filters, adjustments, text layout (`Text/TextLayout`, `Text/TextEditor`), layer effects (`Rendering/LayerEffectsRenderer`), file IO (including the Photoshop reader in `IO/Psd`) and `EditorSession` (every editing command, split into partial files by area). It must never reference Avalonia.
- `src/Composa.App`: the Avalonia desktop app. UI is built in C# (no XAML). `CanvasView` owns viewport, overlays and pointer tools (text editing in `CanvasView.Text`, rulers and guides in `CanvasView.Guides`); `LayersPanel` the layer stack and effect rows; `SideDock` the right-hand column, the Layers panel on top and the Window menu's sections (`HistoryPanel`) under it; `MainWindow.*` the menus, shortcuts (a `Shortcut` table for menu commands and tool keys, rebindable through `ShortcutsDialog`), tabs, options bar and file handling.
- `tests/Composa.Core.Tests`: xUnit tests that drive `EditorSession` directly.
- `tests/Composa.App.Tests`: Avalonia headless tests with real Skia rendering. They save screenshots to `artifacts/screenshots/` (git-ignored), which is the way to check UI changes visually without a display. Every screenshot goes through `Screenshots.Save`, never `CaptureRenderedFrame().Save`: Avalonia encodes through an image that only points at the frame's pixels, so a frame nothing holds on to can be collected during the encode and the test process dies with a segmentation fault. A zero-byte screenshot in the CI artifact marks the test that was saving when that happened.

## Rules that keep the editor correct

- Bitmaps are immutable once they are part of a committed document. An edit copies the bitmap, changes the copy and swaps it into the layer. Undo snapshots (`Document.Clone()`) share bitmaps with the live document, so mutating or disposing a committed bitmap corrupts history and can crash in native code. Only dispose bitmaps you created during the same uncommitted edit.
- Color bitmaps are `Rgba8888` premultiplied; masks and selections are `Alpha8`. Create them through `Pixels.NewColor` and `Pixels.NewMask`.
- A high precision source is associated with its RGBA8888 editing preview by `Rendering/DeepPixels`: `Source(preview)` returns shared immutable RGBA16-unorm (or extended-sRGB floats), never something a caller may mutate or dispose. `Pixels.Clone` preserves the association with an independent byte snapshot of the unpainted preview; changed paint replaces only changed source pixels. Project format 7 stores a 16-bit PNG source (or float OpenEXR for HDR) instead of the preview, and old project versions remain readable. Never feed wide native pixels to a byte-based tool or filter without an explicit precision-aware path.
- After changing a bitmap's pixels in place (only allowed during an uncommitted edit) call `Pixels.Invalidate(bitmap)` so cached `SKImage` wrappers are dropped.
- Every user-visible change goes through `EditorSession.Begin`/`Commit`/`Cancel` (or `Apply`) so it is undoable, then raises `Invalidate`/`InvalidateAll` and `LayersChanged` as needed.
- Saving snapshots the document (`Document.Clone()`, which shares the immutable committed bitmaps) and writes it off the UI thread, exactly as `Recovery` does; `MarkSaved(path, revision)` then clears the modified flag only when nothing changed since the snapshot. The window keeps the saves still writing in `saving`: a second save of the same document waits for the first, and `CloseSession` and `OnClosing` wait for them all, so a file is never cut short. Never snapshot while a drag is mutating a bitmap in place (`Execute` already refuses commands while the canvas is dragging).
- `DocumentRenderer.Render` splits large areas into bands rendered in parallel. Anything added to the render path must be a per-pixel operation that does not depend on neighbouring bands, or it must report a `SamplingMargin` (as the blur adjustments do): the renderer then draws each band with a halo that wide around it and leaves the halo out again, `EditorSession.AffectedArea` grows invalidations by it, and the halo stops at the canvas, whose edges a spatial adjustment must continue (clamp) rather than fade.
- Never invalidate a visual or raise layout-affecting events from inside `CanvasView.Render`.
- Avalonia's X11 backend sends text input only for a key press nobody marked handled. Key handlers must leave printable keys unhandled while text is being typed; the headless tests feed text directly, so check `e.Handled` in a test when touching key routing.
- Every history state has an id (`History.CurrentId`) that travels with its entry between the undo and redo lists. `IsModified` is the current id differing from the one saved, so a save records the id of the state it wrote (`MarkSaved(path, state)`, taken with the snapshot), and undoing back to it makes the document unmodified again. Something that changes the list after its commit announced it, as `History.MergeLast` does, goes through `EditorSession.FoldLastStep`, which raises `HistoryChanged` again. `GoToHistory` moves any number of steps with one restore; keep it one restore, since the History panel scrubs with it.
- The History panel picks each row's icon from the step's name (`HistoryPanel.IconFor`), because the names are the Edit menu's words and already say what a step did. A new step name that is neither a layer step nor covered by a rule there needs a line.
- The dock's sections are `DockSection`s kept in `Settings.Dock` by title. A section's content leaves its old frame before every layout, and the column has a fixed width, so a long step name is cut off rather than widening it.
- Layer lists are stored bottom to top; the Layers panel shows them reversed.
- Sliders in the options bar are `Controls/SliderField` (through `Ui.SliderField`), a box whose fill is the slider: drag to change, Alt-drag for ten times finer steps, double-click to type, wheel and arrows step by one, and a tooltip says so. There is deliberately no Shift multiplier. Setting `Value` from code redraws without raising `Changed`, which is what the bar's refresh relies on. Every control in the bar takes `SliderField.DefaultHeight` through the `options` class styles in `Palette.Styles`, so a new control added to the row lines up without its own height. The dialogs use the same field at one width per dialog so their right edges line up; there is no other slider helper. A field given a `Track` (colors from `Controls/SliderTracks`, which mirror the macOS app's Camera Raw tracks) paints them along the box, dim past the value and bright up to it, with a shadow under the text. A field given a `Reset` shows a Reset button on the left of the box while the editor is open; double-click stays typing, and the button is the reset. Reset means the value that changes nothing (a new adjustment's or a fresh Camera Raw grade's value), never what the dialog opened with, except for filters, which always open at their defaults. Angles get `Controls/AngleDial` beside the field through `Ui.AngleField`, as the shadow effects have: degrees counterclockwise from the right, straight left reads 180, and the dial wraps instead of stopping. The hand points at the light with a bright dot at its tip and a dim stub opposite for the shadow; keep that pairing, because the number is Photoshop's light angle and the shadow falls the other way. Motion Blur's dial is `AngleDialStyle.Line`: a line through the centre with a dot at the end the number counts towards, turning the full circle from -180 to 180 as Photoshop's field allows, although 200 blurs the same as 20; a dial that turns half way feels stuck.
- Layer effects are drawn from an image the renderer caches per (pixels, mask, effects); the image already has the mask applied, so `RenderUnit` must not apply the mask again when effects are present. `Layer.VisibleBounds` includes the effects' margin and is what invalidation uses.
- Every size ceiling lives in `Model/DocumentLimits`; never spell 30,000 or a megapixel count as a literal, and quote them in messages from the constants. Two ceilings are kept apart: `MaxSurfacePixels` bounds any one canvas, layer, mask or export, and `DocumentPixelBudget` (scaled to the machine's memory) bounds the raster a whole document may hold. Importers take what is left of the budget (`Document.RasterPixels()`), and a Photoshop file's canvas is a size, not an allocation, so only its layers count. `PsdReader` crops layers and masks to the canvas only when the file would otherwise be refused, deciding from the records before any pixels are read with the same check the decoder applies.
- SVG files go through `IO/SvgImporter` and `IImageMagick.Rasterize` (density scales the declared size), never through Skia. Fit an SVG to the canvas as it is drawn, not by scaling its pixels afterwards.
- Marching ants: an outline with more than `CanvasView.FullDetailPoints` points is drawn below 1:1 from `SelectionMask.ReducedOutline`, cached per power-of-two zoom step and rebuilt in `Render` when the step changes. The ants timer skips a tick while a redraw it asked for is still pending (`antsRedrawPending`), so a slow outline stutters instead of queuing redraws.
- A Color Lookup's table is a `ColorLattice` (`Filters/ColorLookup.cs`): immutable, red-fastest floats, named by the SHA-256 of its contents. The adjustment holds the lattice itself, never a path, so undo snapshots share it as they share bitmaps; the JSON carries only `LatticeId`, and `ProjectFile` (format 6) writes the lattice once as `lookups/<id>.bin` however many layers share it. `ContentEquals` sees the id, which is how a dialog tells a new table from the old one. The bundled looks (`Filters/Looks.cs`) are embedded from `Looks/*.cube`, made by `scripts/make-looks.sh` from FilmSim's CC0 tables under descriptive names because the stock names are trademarks; their provenance is in `packaging/THIRD-PARTY-NOTICES.txt`, which ships with every build for that reason. Export Look (`Filters/LookBake.cs`) bakes only what is a function of color: it mixes by opacity alone because `DocumentRenderer.Mix` applies no blend mode to an adjustment layer, and an adjustment that reads its position says so through `DependsOnPosition`.
- Text layers are re-rendered from their `TextStyle` through `TextLayout` on every change. The layout's character positions are the caret geometry; keep drawing and layout in that one class so what is typed is what is rendered.
- Letters in their own colors are `TextStyle.ColorRuns`, character ranges over `Text` that are null when the text is one color. `TextStyle` spells out its own equality because the runs are a list and styles are compared everywhere to tell a change from none: a new property goes into `Equals` and `GetHashCode` too. Anything that changes `Text` calls `WithReplacedCharacters` first so the colors stay on their letters, as `TextEditor` does; `WithColor` with an empty or whole range means one color and drops the runs; `AsDefaults` is what the next text starts from. A color from the Type bar or the foreground picker goes through `EditorSession.SetTextColor`, which paints the selection while typing and all of the text otherwise, and a cancelled picker calls `RestoreTextColors` with the style it opened on.
- `EditorSession.TextEdit` is an open edit (a `Begin` without `Commit`); anything that starts another edit or changes the tool or layer selection must go through `FinishText`, which `FinishInteraction` and `SelectLayer` already do.
- A change in the Type bar with a text layer active but not open for typing restyles the layer in place (`ChangeTextStyle`), never through `EditText`: opening the editor would take the keyboard from the bar's field and hand what is typed next to the text. Every keystroke in a field is a change, so consecutive changes on one layer are folded into one undo step through `History.MergeLast`.
- View options (rulers, grid, guides, snapping) live on `EditorSession.View` and are carried from tab to tab like the tool settings; guides themselves are document data and undo with it. The window copies them, Auto Select, the transform controls and the pixel grid into `Settings` on every change (`RememberToolSettings`), and the first document of a launch starts from `Settings.View`, so they survive a relaunch. Tests run with `Settings.Persist` off and read the window's `Settings` back.
- Blend modes Skia cannot draw (`BlendMode.IsCustom`) are composited per pixel by `Rendering/SeparableBlend` from a finished tile sibling, so they take the general path in `RenderUnit`, never the fast raster path. A new mode needs its function there, a display name, a key in `PsdImport.Blends` and a place in `BlendModeExtensions.Groups`, which is the menu order. A mode Photoshop does not have (Grain Extract and Grain Merge are GIMP's) gets no key, which is fine because Photoshop is only read: it simply never comes out of a Photoshop file, and `XcfImport.Table` maps GIMP's number to it instead.
- The Camera Raw Filter lives in `Filters/CameraRaw.cs` (settings records, all with `Normalized()` clamps and an `Adjusts` flag per group) and `Filters/CameraRawPixels.cs` (the pipeline, stage for stage as the macOS app's C code: calibration, Light and Color, curve and mixer and grading, effects, grain, optics, detail). Every stage reads straight color and writes premultiplied bytes back; keep new stages row-parallel and alpha-preserving. The panel (`Dialogs/CameraRawDialog.cs`) hides a group by rendering `Without(group)`, so OK returns the grade as rendered. Save Look bakes a grade through `LookBake.Bake(CameraRawSettings, …)`, which runs `CameraRawPixels.Apply` itself on the identity grid without `LookBake.SpatialGroups` (Effects, Detail, Optics); a new stage that reads neighbours or the position belongs in one of those groups, or the saved table will not match the picture.
- Camera Raw's measured Light/Color, primary calibration, default parametric regions, mixer and grading tables are in `CameraRawTables.cs`; `CameraRawMeasuredColor.cs` composes the stages on a 33-cubed float grid before applying them. `CameraRawShadows.cs` is a separate guided regional pass between Highlights and Whites. Data in `CameraRawData/` is pinned to Compositor v1.5.3 and regenerated by `scripts/import-compositor-tables.py`; its MIT notice must travel with every package. A group's `ResetGroup` resets all controls, while `Without` retains inactive choices for the group's visibility toggle.
- Filters that push pixels past a layer's edges (`FilterSettings.Spreads`) return a grown bitmap with how far it grew; `EditorSession.Preview` shifts the layer back by that much. Vignette on an empty layer needs the layer grown to the canvas first, which `EditorSession.BeginFilter` does.
- The Dither filter is `Filters/Dither.cs` (settings, with `Normalized()`, the style flags and the menu groups) and `Filters/DitherPixels.cs` (the pipeline, stage for stage as the macOS app's C code: tone, then diffusion or an ordered threshold quantized to tones, or halftone, pattern and glyph marks; chunky pixels average the layer down, dither it and blow it back up). Per-pixel stages are row-parallel; diffusion is serpentine and sequential by nature. ASCII glyphs are drawn once per distinct character with Skia's bold monospace face at the text size and sorted by ink; the image is never shrunk for it.
- The Painterly filter (`Filters/Painterly.cs`) is Hertzmann's painterly rendering: the largest brush first, each smaller brush only where the canvas still differs from the picture softened by that brush, strokes started at a cell's worst pixel, colored from the picture and run along its edges. The style record holds the paper's parameters and `Detail` scales its threshold. Strokes are dabs with the brush engine's falloff, tabulated per pass, painted in parallel by bands with the colors drawn beforehand, so the same seed always gives the same picture; keep any change to the painting order deterministic. Gaps between strokes stay transparent by design.
- Camera RAW files go through `IO/RawImporter`: ImageMagick (LibRaw) decodes to a 16-bit PAM that `RawImage` parses, and `RawImage.Develop` builds one 16-bit-to-16-bit table per channel and an associated editing preview. Noise reduction, highlight recovery and manual lens distortion are applied before import. The develop dialog previews from a sampled reduction; the import develops the full frame once, both off the UI thread.
- Brush Smoothing is a string length in screen points, so `EditorSession.ViewZoom` must be set by the canvas before a stroke starts and while it runs; the first dab always lands, the last one catches up to the pointer on release.
- The Photoshop reader (`IO/Psd`) is written from Adobe's published Photoshop File Formats Specification and must stay free of code taken from GPL readers. `PsdReader` only parses and decodes; `PsdImport` turns records into layers and the conversion report, and `PsdVector` and `PsdAdjustments` map shapes and adjustments. Photoshop is read, never written. `tests/Composa.Core.Tests/PsdWriter.cs` builds fixture files and is shared into the app tests by source.
- The GIMP reader (`IO/Xcf`) is written from GIMP's published description of the format (developer.gimp.org, "XCF file format") and from Lolly's reader, and must stay free of GIMP's own code: never read `xcf-load.c` or any GPL reader. `XcfReader` only parses and decodes, `XcfImport` turns records into layers and the conversion report (`ImportConversion`, shared with Photoshop files), and the test project's `XcfWriter` builds fixtures for every version family, compression and precision. XCF is read, never written. Pointers are 4 bytes before XCF 11 and 8 from it, a layer carries a list of effect pointers from XCF 20 and the image a third pointer list for paths from XCF 18; a tile pointer outside the file costs that tile, anything else damaged refuses the file. Every precision is converted to 8-bit sRGB (linear samples through the sRGB curve, coverage only scaled), and groups come from `PROP_ITEM_PATH`. A top-level layer carries no item path in GIMP's own files, so its path is its place among the roots. GIMP 3.2.6 declares `PROP_LINK_LAYER` four bytes short of what it writes, and the property walker steps over the height that follows. `XcfText` maps the `gimp-text-layer` parasite (GIMP 2.10's one-string font and `color-rgba`, and GIMP 3's `GimpFont` form and GEGL color with octal-escaped float bytes) onto `TextStyle`; text with markup stays pixels. `tests/Composa.Core.Tests/Fixtures/Xcf` holds files GIMP 3.2.6 wrote with `make-fixtures.py`, run by hand through the Flatpak's `gimp-console-3.2`, and `XcfFixtureTests` holds the reader to them; the stored pixels of a layer with effects are without the effects.
- Every on-device model is an `OnnxModel` record in `Composa.Core/Vision` (file, SHA-256, size, licence, source), loaded through `ModelRunner`, which hashes the file before its first load, runs on the CPU with a fixed thread count and cancels through `RunOptions.Terminate`. The Enhance choice of Image Size is `Upscaler.Enlarge` (ported from Lolly): Real-ESRGAN general v3 (`realesr-general-x4v3.onnx`, 4.9 MB, BSD-3-Clause, in git) enlarges four times, tile by tile (`Upscaling.PlanTiles`, 256 with 16 of overlap), on straight RGB with the colors spread into transparent pixels first and the alpha enlarged on its own; `EditorSession.PrepareEnhancedAsync` runs it off the UI thread over the committed pixels and `ResizeImage` takes a prepared result only while the layer still shows the bitmap it was made from (`EnhancedLayers.For`), so the slow part never runs inside `Apply`. Layer > Enhance Resolution reuses that path for one layer (`PrepareEnhancedResolutionAsync`, `EnhanceResolution`): the pixels grow to the layer's size on the canvas, at most four times, the transform's Width and Height stay as they are so the placement does not move, and a layer that lands on one pixel per canvas pixel is made a plain identity placement again. Lolly's x4plus, illustration and GFPGAN models do not ship: too slow on a CPU, a torch conversion, and invented faces.
- Subject detection lives in `Composa.Core/Vision`: `SubjectModels` is the catalog (file, SHA-256, size, licence, input size, mean and std, activation), `ModelRunner` runs a model through ONNX Runtime on the CPU with a fixed thread count and checks the file's hash before its first load, `Matting` is the letterbox and tensor arithmetic ported from Lolly, `SubjectMatting` the pipeline and `GuidedFilter` the edge-aware upsampling from the model's 320 or 512 pixels to the picture's size. `SubjectFinder.Resolve` turns the `SubjectDetect` choice into what actually runs: the plain backdrop whenever the runtime did not load or the file is missing, so no command can fail that worked before. **Only weights under a permissive licence (Apache-2.0, MIT, BSD) are listed**; BRIA's RMBG models are non-commercial and never ship. `u2netp.onnx` (4.6 MB) is in git under `Composa.Core/Models`; `modnet.onnx` (26 MB) is git-ignored there and fetched, pinned and checksummed, by `scripts/models/fetch.sh`, which the packaging scripts and the workflows run; a checkout that has not run it works without the Person choice and the tests say so. A new model goes into the catalog, the fetch script and `THIRD-PARTY-NOTICES.txt` in one change. The models are read from `SubjectModels.Directory` (`COMPOSA_MODELS_DIR`, else `models/` beside the application) and never downloaded at run time. `EditorSession` runs a model off the UI thread on a committed bitmap (immutable, so read in place) or a copy of the composite, through `ProgressWindow.Run`, throws the result away when `History.CurrentId` moved meanwhile, and keeps the matte per (picture, choice) so a Select Subject after a click costs nothing. Remove Background with a model adds a mask and meets an existing one (multiplies), never replaces it. A dragged box with the Object Selection tool (`SelectObjectInBoxAsync`) runs the model on the crop alone and bypasses the matte cache, because a crop is its own picture.
- Files ported from Lolly (github.com/lolly-tools/lolly, MPL-2.0) start with a header naming the source path and commit and the MIT permission Andy Fitzsimon gave on 2026-09-30; `Filters/ColorLookup.cs` and its tests are the first. Keep that header on anything else taken from there, and if the permission is ever questioned the file goes back to MPL-2.0, which may sit inside the MIT application as a separately licensed file.

## Releasing and packaging

- **The version comes from the nearest git tag, through MinVer. Never hand-edit a version anywhere.** An untagged commit builds as a pre-release of the next patch, so a development build reports something like `0.3.1-alpha.0.4` and is never mistaken for a release. Every checkout in CI needs `fetch-depth: 0`, or MinVer sees no tags and silently versions everything `0.0.0`. `AppInfo.Version` is the single place that reads it back, stripping the `+<sha>` build metadata.
- **A test must never compare against `AppInfo.Version`.** It changes with the tag: the same assertion exercises a stable version on the day of a release and a pre-release the day after. `UpdateCheck` takes the running version as a parameter for exactly this reason, and tests state the versions they are about.
- **Linux artifacts build on `ubuntu-22.04`, never `ubuntu-latest`.** A self-contained build links against the build machine's glibc, and 24.04 output refuses to start on Debian 12 or Ubuntu 22.04. The pin is deliberate and commented in both workflows.
- `scripts/package/all.sh [rid] [out]` builds every Linux format; `stage.sh` lays out the one tree that the `.deb`, `.rpm` and AppImage all pack, so a layout bug is fixed once. The tarball is the only single-file build. `scripts/publish.sh` is now a thin wrapper around the tarball.
- **Packaging scripts resolve output and staging directories to absolute paths as they read them**, because several of them `cd` into a temporary directory before writing. CI passes a relative `dist`, and a script that skips this writes the package somewhere nobody looks.
- Every format spells architectures differently (`amd64`/`arm64` for dpkg, `x86_64`/`aarch64` for rpm and AppImage, `x64`/`arm64` for the .NET RID) and neither dpkg nor rpm accepts the `-` in a MinVer pre-release. Both mappings live in `scripts/package/common.sh` and belong nowhere else.
- `ci.yml` builds and tests on Linux and Windows for every pull request and every push to `main`, except changes to nothing but Markdown. `packages.yml` builds the x86-64 Linux packages and the Windows zip and installer, but only for pull requests that touch `scripts/`, `packaging/`, the workflows or the MSBuild and SDK files, and on demand through **Run workflow**. Those jobs exist because the scripts were once exercised only by a release, which meant a release rehearsal was the first thing to discover they could not run from a clean checkout; **when a new file starts to affect packaging, add it to the `paths` list in `packages.yml`**, or a change to it goes unchecked until the next release.
- Because package builds no longer run for every change, the Linux `build` job compiles the app once more with `-p:BundleImageMagick=false`, the configuration only Linux packages use. It is what catches code that uses `BundledImageMagick` outside `#if BUNDLED_IMAGEMAGICK`.
- Skipped workflows report no check at all. `main` has no required checks today; if that changes, a Markdown-only pull request, or one that does not touch packaging, would wait forever for a check that never runs, so required checks need a different approach than path filters.
- `RELEASING.md` is the procedure: fill a **draft** release through a workflow dispatch, check it, then publish. A published release with no artifacts attached is worse than no release, because the update check points people at whatever is latest. GitHub creates the tag when the release is published, so no tag is ever pushed from a terminal.

- **Magick.NET is bundled for every RID except Linux ones**, through the `BundleImageMagick` property in `Composa.App.csproj`. Linux packages leave out its 36 MB native library because the distributions ship ImageMagick; a developer build has no RID and bundles it, which is why the bundled path is tested on Linux too (`BundledImageMagickTests`). Code that uses it sits behind `#if BUNDLED_IMAGEMAGICK` or in `BundledImageMagick.cs`, which is left out of compilation otherwise.
- **The licence notices travel with the library, never separately.** Bundling redistributes LGPL libraries (libraw, libheif, libde265 among them), so `THIRD-PARTY-NOTICES.txt` and Magick.NET's own notice (`ImageMagick-NOTICE.txt`) are items in the same conditional block as the package reference, and `windows.sh` refuses to package a build without them.
- A publish drops every `.pdb`: SkiaSharp and HarfBuzzSharp ship 105 MB of native symbols for Windows that `DebugType=none` does not cover.
- Composa's own folders come from `AppPaths` (XDG on Linux, `%APPDATA%` and `%LOCALAPPDATA%` on Windows, Application Support and Caches on macOS), and so does the person's Downloads folder: `XDG_DOWNLOAD_DIR` from `user-dirs.dirs` on Linux, so a localised folder is found, the Downloads known folder on Windows, `~/Downloads` otherwise. Avalonia's `WellKnownFolder.Downloads` is not used, because on Linux it reads only an environment variable nothing sets. Nothing else builds a config, cache or Downloads path.
- `scripts/package/windows.sh [rid] [out] [--no-installer]` publishes one tree and packs the zip and the Inno Setup installer (`packaging/windows/composa.iss`) from it. It runs in Git Bash on Windows and, without the installer, on Linux. Neither Windows build is single-file: that would unpack 40 MB of native libraries into `%TEMP%` on first launch. **The installer's `AppId` must never change**, or a new version installs beside the old one instead of upgrading it.
- `.gitattributes` forces LF on `*.sh`, because the Windows runners run them in Git Bash and bash rejects CRLF scripts.

## Rules for what the application tells the user about itself

- `UpdateCheck` reports that a newer release exists. A stable build is never offered a pre-release; a pre-release sorts before the version it leads to; skipping applies to one version only.
- **Composa never downloads on its own, never installs, and never replaces its own files.** `UpdateDownload` fetches a file only when the person presses Download in the strip, only from this repository's releases over HTTPS (`ReleaseAsset.IsOwnAsset`), with the same bare `User-Agent: Composa` as the check, into the Downloads folder. It writes `<name>.part`, gives the file its name only once its SHA-256 matches the release's `sha256sums.txt`, and leaves nothing behind on a failure or a cancel; a release without that file downloads nothing, so the release workflow must keep writing it under that name. Install hands the checked file to the program whose job it is (`Installer`): the Windows setup after quitting through `ConfirmQuit`, the same path File > Quit takes, and a `.deb` or `.rpm` to the desktop's software installer with the apt or dnf command offered beside it. Replacing the running application's files would be self-update, which is out of scope.
- **The file an update downloads depends on how the running copy was installed, which only the running machine can say.** The `.deb`, `.rpm` and AppImage are packed from one staged build and the Windows zip and installer from one published tree, so `Install.Detect` looks at run time: the AppImage runtime's `APPIMAGE` and `APPDIR` (and the application running inside that mount), dpkg's file list or rpm's owner of `/usr/lib/composa`, and the Inno Setup uninstall key built from the installer's fixed `AppId`. A build with no `RuntimeIdentifier` (recorded in the assembly as the channel is) is a developer build and is offered the release notes only. Every probe is passed in, so each kind is tested on any platform.
- **The release file names are matched in `ReleaseAssets` as well as written by the packaging scripts.** A package renamed in `scripts/package` needs the same change there; `ReleaseAssetsTests` holds v1.2.0's real asset list to catch the day they drift apart. Files are matched by how their names begin and end (format and architecture), never by the version between, which dpkg, rpm and GitHub each spell their own way.
- `FileReveal` is the one way to show a file selected in the file manager: Explorer's `/select` on Windows, `open -R` on macOS, and on Linux `org.freedesktop.FileManager1.ShowItems` sent through Tmds.DBus.Protocol, which Avalonia's Linux backend already brings; where that fails the folder is opened with Avalonia's launcher. The tab menu's Show in Folder and the update strip both use it.
- **No test reaches GitHub or starts a program for an update.** Everything the window reaches for (the releases, the network, the Downloads folder, the install kind, the programs Install and Show in Folder start) goes through `MainWindow.Updates`, an `UpdateEnvironment` a test replaces, and the automatic check does not run with `Settings.Persist` off, since its once-a-day limit lives in the settings file.
- **A build that comes from a repository must never mention updates.** The `UpdateChannel` build property is read back from assembly metadata; at `managed` the Help menu explains that the package manager owns updates instead of pointing people around it. Every download on the releases page, the `.deb` and `.rpm` included, is on the `github` channel: they are installed by hand from a file, so no repository will ever update them, and a managed build there would leave its users stranded on the version they downloaded. Only a package that really comes from a repository is staged with `UPDATE_CHANNEL=managed`.
- An automatic check that fails says nothing, but still records the attempt: otherwise someone offline or rate limited by GitHub sends another request on every launch.
- `ImageMagick` (in `Composa.Core/IO`) resolves once which `IImageMagick` to use: `ImageMagickTool`, the installed command line, or `ImageMagick.Bundled`, the Magick.NET library that `Program.Main` registers in builds that carry it. Linux prefers the tool, everything else the bundled library. The tool asks each candidate to identify itself rather than trusting its name. **Never probe for `convert` on Windows**: `C:\Windows\System32\convert.exe` is the FAT-to-NTFS volume converter and is on the PATH of every Windows machine.

## The MCP server

- The server lives in `src/Composa.App/Mcp/`: `McpHost` listens on a per-user pipe (`McpPipe.Name`, a Unix socket under the cache folder on Linux and macOS, a named pipe on Windows, overridable with `COMPOSA_MCP_PIPE`) and runs one `McpServer` per connection; `composa --mcp` (`McpBridge`) is the stdio bridge a client launches. Only `ModelContextProtocol.Core` is referenced: no ASP.NET Core in a desktop app.
- **Every tool runs on the UI thread through `EditorSession`** (`OnUi` in `ComposaTools`), so an agent's change is one undoable step and the window repaints as it happens. A tool that edits goes through `Editable()`, which refuses while the canvas is dragging or an edit is open and commits text being typed first, as a menu command does. Tools that address a layer select it only when the command acts on the active layer, and put the active layer back afterwards.
- Tools and resources are gathered by reflection from `[McpServerTool]` and `[McpServerResource]` methods on the `ComposaTools` partial class, one file per area. A new tool goes into the sorted name list and the scenario of the end-to-end test in `tests/Composa.App.Tests/McpTests.cs`, which launches the real `composa.dll --mcp` and therefore needs `dotnet` on the PATH. Never start a `McpHost` on the default pipe name in a test: pass a name or set `COMPOSA_MCP_PIPE`. In the headless tests the server's UI work runs only while the test pumps, so wrap every client call in `Pumped`. `CallToolResult.IsError` stays null on success. `BlobResourceContents.Blob` holds base64 text as bytes: build one with `FromBytes` and read `DecodedData`.
- **The bridge answers the client's `initialize` itself and outlives the application.** It replays the handshake to the application on every pipe connection (id `composa-bridge-initialize`), holds requests during that handshake, advertises `listChanged` for tools and resources and announces both each time the application comes or goes. While the application is away `tools/list` and the resource lists answer empty, `ping` answers, other requests get error -32000, and requests in flight get an error instead of hanging. The bridge exits only when the client closes stdin. `--launch` starts the application at most once, when the first connection fails; a later quit is the person's.
- File tools go through the window's own commands with the dialogs cut out (`MainWindow.OpenPath`, `MainWindow.SaveTo`), so a save from an agent is written in the background as Ctrl+S is and close and quit wait for it. Photoshop and RAW files are refused because they need a dialog. A file at a path the document did not come from is never replaced without `overwrite`.
- The tools an agent draws with are grounded in the pixels, because a language model estimates coordinates from a rendered view and gets them wrong by tens of pixels: `render` takes a `grid` (labelled in canvas coordinates) and a region, `sample_color` averages a disc, `trace_edges` (`Painting/EdgeTracer`, Canny with a one-pixel gap bridged in chain following) returns polylines longest first, and `paint_strokes` paints a batch as one undo step through `EditorSession.PaintStrokes`, which folds the entries with `History.MergeLast`. Reading a layer's own pixels goes through the inverse of `Layer.Matrix`, so a reference under the agent's strokes can still be read.
- Composa's `render` result and the image resource are PNGs of `EditorSession.Composite()`, which the session owns: scale a copy, never dispose it.
- Claude Code refreshes its tool list on the bridge's `tools/list_changed` (its MCP log says "refreshing tools"; the desktop app ignored it before 2026-09-26, anthropics/claude-code issue #50339), so a Composa started or restarted while a session runs brings its tools along. The bridge's command line is read only when the client spawns it, so a change to the registration, such as adding `--launch`, needs a Claude Code restart.

## Precision and print proofing additions

- `DeepAdjustments` operates on native float render tiles. `DeepFilters` uses native spatial sampling and the pinned Compositor split/reconstruct method for byte-only effects. Preserve the immutable native source; only the preview is RGBA8888.
- `CmykProof` owns an ICC round-trip lattice for display and delegates print conversion through `IColorConverter`. Proof colors and gamut warning never modify document pixels. CMYK PDF uses native four-channel samples with its ICC profile embedded.
- Camera Raw uses a Skia runtime shader for eligible single-layer color grades. Spatial stages, selections, proofing and layered documents use `PreviewFilterAsync`; close waits for in-flight preview work before accepting the final grade. Always clear the canvas shader frame before committing or cancelling. No performance claim is inherited from upstream without a benchmark.
- `Magick.NET.Core` provides the same managed ICC resources on every platform. Only bundled builds carry the HDRI native library and its native notice; the managed Apache licence travels with every build.
